# Tofu gallery copy

This repository is Tofu's copy of **babybuddy/babybuddy** (licence: BSD-2-Clause), listed in Tofu's app gallery as a **baby care log**: Baby Buddy, where the people who look after a baby record its feedings, sleep, diaper changes, tummy time, pumping, medication, temperature and growth, and see them on dashboards, a timeline and charts.

- `master` mirrors the upstream repository and is never committed to by Tofu.
- `tofu` carries Tofu's own changes; tags named `pin/<date>` mark the versions the gallery points to. The current pin is `pin/2026-10-26`. It replaces `pin/2026-10-25.1`, on which the instances Tofu starts at once on a new database crashed against each other making the same tables, every start sent hundreds of statements through the pooler before it listened on its port, and the app's tables were open to the database's Data API (see "Start-up when several starts run at once"). `pin/2026-10-25.1` replaced `pin/2026-10-25`, on which a picture or image sent through the REST API or the admin's note form was kept on the container's disk (see "What works differently on Tofu").
- A visitor who chooses this app gets a private snapshot of the pinned version in their own Tofu account. Their copy does not follow upstream updates.
- Upstream: https://github.com/babybuddy/babybuddy at `09629cf633cf3a2059a21ade4cea7ea4d846422f` (2026-10-12, v2.11.0 plus 34 commits).

## How Tofu runs it

- Framework preset `container`, root folder: the repository root. Tofu builds the root `Dockerfile` and runs the image as a service, so there is no separate install command, build command or output directory.
- The `Dockerfile` is Tofu's own (upstream has none at its root). It starts from `python:3.13-slim`, installs `requirements.txt` with pip (every requirement has a Linux wheel for Python 3.13, so nothing is compiled), copies the repository and starts `tofu-entrypoint.sh`. Upstream commits its compiled styles, scripts, icon font and images under `static/`, together with WhiteNoise's manifest, so the image runs no Node build (`gulp`) and no `collectstatic`.
- `tofu-entrypoint.sh` runs `python manage.py tofu_schema`, the schema step, where upstream's `Procfile.sh` runs `migrate` (see "Start-up when several starts run at once"), retried up to five times five seconds apart while a new database is still starting, then `gunicorn babybuddy.wsgi:application` on `0.0.0.0:$PORT` (80 without `PORT`) with `WEB_CONCURRENCY` workers (2 when unset).
- Settings: the image sets `DJANGO_SETTINGS_MODULE=babybuddy.settings.tofu`, which takes upstream's `babybuddy/settings/base.py` and changes only what is listed under "What Tofu changes".
- Database: PostgreSQL, the app's Tofu database, read from `DATABASE_URL` by upstream's own settings (`dj-database-url`). The tables are those of upstream's Django migrations: a new database gets them from a snapshot of those migrations in one statement, and a database with migrations left to apply gets `migrate` (see "Start-up when several starts run at once"). The cache table `cache_default` is made by upstream's migration `babybuddy/0029`. The repository has no `supabase/migrations` folder, so Tofu applies no SQL of its own. Every start turns on row-level security on each table the app makes, which closes them to the database's Data API.
- Environment: Tofu sets `PORT` and `DATABASE_URL`, and a gallery copy saves `CSRF_TRUSTED_ORIGINS` set to the copy's own address. Nothing has to be set by hand before the first deploy. Settings an owner may add are named below: `SECRET_KEY`, the upload settings, the mail settings, and `CSRF_TRUSTED_ORIGINS` or `ALLOWED_HOSTS` for a domain of their own.
- Logs: gunicorn writes each request to standard output, and Django's warnings and errors go to standard error (see "What Tofu changes"), so the app's runtime log on Tofu shows them.
- Upstream's files for other hosts (`Procfile`, `Procfile.sh`, `.buildpacks`, `runtime.txt`, `nixpacks.toml`, `.do/`, `terraform/`) stay as they are; Tofu uses none of them.

## What Tofu changes

- `babybuddy/settings/tofu.py` (new), on top of upstream's `base.py`:
  - `ALLOWED_HOSTS = ["*"]` unless `ALLOWED_HOSTS` is set. Upstream's default is one empty host name, which with `DEBUG` off answers every request with 400, and the image cannot know the copy's address.
  - `SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")` and `USE_X_FORWARDED_HOST = True`. Tofu serves the app over HTTPS through its own proxy, so Django reads the scheme and host the visitor used from the proxy's headers. Django's CSRF check compares every form's `Origin` with them.
  - `SESSION_COOKIE_SECURE` and `CSRF_COOKIE_SECURE` are true unless set to false (upstream: false).
  - When `DATABASE_URL` is set: `DISABLE_SERVER_SIDE_CURSORS = True`, because Tofu's `DATABASE_URL` goes through a transaction pooler, which keeps no cursor from one transaction to the next; and `CONN_MAX_AGE = 60` with `CONN_HEALTH_CHECKS = True`, so each worker keeps its connection for a minute, checked before reuse, instead of opening a TLS connection for every request.
  - When `SECRET_KEY` is not set and `DATABASE_URL` is, `SECRET_KEY` is the SHA-256 of `baby-buddy-secret-key:` followed by the whole `DATABASE_URL`, written as 64 hex characters. See "The secret key".
  - `BABY_BUDDY["ALLOW_UPLOADS"]` is false unless `ALLOW_UPLOADS` is set (upstream: true). See "What works differently on Tofu".
  - `BABY_BUDDY["FIRST_ACCOUNT_SETUP"] = True`. See "The first account".
  - `LOGGING`: the `django` loggers' warnings and errors go to standard error. Upstream keeps Django's default logging, which with `DEBUG` off sends a request's error (a 500 and its traceback) only by mail to `ADMINS`, and a copy has none, so the runtime log showed nothing about it. Now it shows a request's error with its traceback, a form refused by the CSRF check with the reason, and each page not found.
- `babybuddy/settings/.gitignore`: names `tofu.py`, because this folder's `.gitignore` ignores every file it does not name.
- `babybuddy/management/commands/migrate.py`: upstream's `migrate` creates a superuser `admin` with the password `admin` whenever there is no superuser. On a public address anyone could sign in with it. With `BABY_BUDDY["FIRST_ACCOUNT_SETUP"]` on, it creates no account. Upstream's settings modules leave the setting off, so their behaviour and upstream's tests are unchanged.
- `babybuddy/first_account.py` (new), `babybuddy/templates/registration/first_account.html` (new) and `babybuddy/urls.py`: the first-account page at `/first-account/`, and the login page, now Django's own login view with one addition: while the setting is on and the app has no account, it sends visitors to the first-account page.
- `babybuddy/tests/tests_first_account.py` (new): the page creating the administrator, the page closed once an account exists, a refused form, and `migrate` with the setting on and off.
- `api/serializers.py`: `UploadFieldsSerializer` (new), used by `ChildSerializer` and `NoteSerializer`, makes a child's `picture` and a note's `image` read-only in the REST API while uploads are off, as the web forms leave them out. Upstream's API took both whatever `ALLOW_UPLOADS` said. A file sent anyway is ignored, the response shows the field empty, and the API's `OPTIONS` answer shows it read-only. With uploads on the API is upstream's.
- `core/admin.py`: the admin's note form leaves the image out while uploads are off, as upstream's admin child form leaves out the picture. Upstream's `NoteAdmin` names no fields, so the admin showed every field of a note, the image included, whatever `ALLOW_UPLOADS` said.
- `babybuddy/tests/tests_uploads_off.py` (new): with uploads off, a picture or image sent to the API (`POST`, `PATCH`) or posted to the admin's note form is not kept and no file is written, the admin's note form has no image field, and `OPTIONS` shows the fields read-only; with uploads on, the API and the admin keep them.
- `requirements.txt` and `Pipfile`: Pillow 13.0.0 instead of 12.3.0, and Django REST framework 3.18.3 instead of 3.18.1. Between 2026-10-20 and 2026-10-23, after upstream's last commit, GitHub published advisories for both pinned versions: memory errors in Pillow's image decoders, some rated critical (fixed in 13.0.0), and in Django REST framework, among others, a denial of service through the `Accept` header that needs no sign-in (fixed in 3.18.2). A copy does not follow upstream, so this pin takes the fixed versions. Pillow 13 needs Python 3.11 or later, so its line in `requirements.txt` now says `python_version >= '3.11'`.
- `babybuddy/tofu_schema.py`, `babybuddy/management/commands/tofu_schema.py` and `babybuddy/tofu_schema.sql` (new): the schema step of every start (`manage.py tofu_schema`) and the snapshot it applies to a new database. See "Start-up when several starts run at once"; `manage.py tofu_schema --make-snapshot` makes the snapshot again.
- `babybuddy/tests/tests_tofu_schema.py` (new): the snapshot holds exactly the code's migrations, each from the same file, turns on row-level security on every table of the app, and changes no setting of the connection.
- `Dockerfile` and `tofu-entrypoint.sh` (new): see "How Tofu runs it".

Nothing upstream was removed. Tofu's safety check has no finding on the repository, upstream's GitHub Actions workflow included (see "Verification").

## The first account

- A new copy has no account. Until one exists, the login page, and so the copy's address, opens "Create the first account". The account made there is a superuser: Baby Buddy's administrator, who adds everyone else (parents, caregivers, read-only users) under the account menu's **Users**.
- Once any account exists, the page closes: it sends visitors to the login page. Baby Buddy has no sign-up of its own, so after that nobody can make an account for themselves, and there is no sign-up setting to close.
- Whoever opens a new copy first gets that page. The owner should open their copy and create their account as soon as it is online. To keep everyone else out even before that, the owner can make the app private on Tofu (people they choose, or an access code) before opening it.
- Each account's time zone is UTC until its user sets it under the account menu's **Settings**; times are entered and shown in that time zone.

## The secret key

- Django signs sign-in sessions and password-reset links with `SECRET_KEY`. Tofu supplies none, so a copy derives one from `DATABASE_URL` at every start (above), and starts with nothing set by hand.
- Anything that changes `DATABASE_URL` changes the key at the next start: a new database password, a different host or pooler address, other query options, or a database Tofu brings back or creates anew under another address. After that start everyone is signed out and has to sign in again, and password-reset links sent before stop working. Accounts, passwords, API keys and the log itself are kept in the database and are not affected.
- To keep sessions independent of the database address, save `SECRET_KEY` as a hidden value on the app's Keys & settings page (for example the output of `openssl rand -base64 48`) and deploy again; that change signs everyone out once.
- The derived key is only as secret as `DATABASE_URL`, which Tofu keeps as a hidden value.

## What works differently on Tofu

- **Child pictures and note images are off.** Upstream lets you add a picture of each child and an image to each note, and keeps the file in `media/` on the server's disk. A copy has no lasting disk: the next restart loses the file while the database still names it, and the pages that show its thumbnail (the child list, the child's page, the note list) then answer with a server error (500). With `DEBUG` off nothing serves that folder anyway. So uploads are off: the web forms and the admin (**Database Admin**) have no picture or image field, and the REST API ignores a `picture` sent to `/api/children/` or an `image` sent to `/api/notes/`, keeps the rest of the record and answers with the field empty. To turn uploads on, set `ALLOW_UPLOADS=true` and point Baby Buddy at an S3-compatible bucket: `AWS_STORAGE_BUCKET_NAME`, `AWS_S3_ENDPOINT_URL` for a bucket that is not on Amazon S3, and the bucket's keys `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` as hidden values; then deploy again. The forms, the admin and the API then take pictures and images, and keep them in the bucket.
- **Webhooks are never sent.** Upstream's webhooks (**Database Admin** → Webhooks, or `/api/webhook-endpoints/`) queue one event per change for every active endpoint, and only `python manage.py deliver_webhooks`, run on a schedule or kept running as a second process (`--every 1`), sends them. A copy runs neither: its container runs the schema step and the web server, nothing else. So an endpoint added on a copy receives nothing, and while it is active every change to a child, an entry or a timer adds a row to the database's event queue (`webhooks_webhookevent`) that is never sent and never removed. Leave webhooks unset on a copy, or switch an endpoint off: an endpoint that is off gets no new events, and those already queued stay. The container does not start the delivery loop itself, because upstream's delivery takes no lock on the queue: with more than one instance of the app running, each would send the same events.
- **Password-reset mail goes to the app's log.** Without `EMAIL_HOST`, Baby Buddy's mail backend is the console, so "Forgot your password?" writes the reset mail, link included, to the app's runtime log instead of sending it. Only the owner can read that log. To send mail, set `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_USE_TLS` or `EMAIL_USE_SSL`, `EMAIL_FROM`, and `EMAIL_HOST_PASSWORD` as a hidden value. An administrator can also set anyone's password in the account menu's **Database Admin** (`/admin/`).
- **The schema step runs at every start, one start at a time**, where upstream's `Procfile.sh` runs `migrate` (see "Start-up when several starts run at once"). A start with nothing left to apply does not run `migrate`, so upstream's post-migrate steps, which make the content types and permissions of new models, the read-only and caregiver groups with their permissions and the default nap times, run only when migrations are applied; on a new database the snapshot already holds what they leave. Upstream's `NAP_START_MIN` and `NAP_START_MAX` variables, which only those steps read (for settings from before Baby Buddy 2.0), therefore change nothing on a new copy: an administrator sets the nap times under the account menu's **Site** → **Settings**.
- **The account menu's "Source Code" and "Chat / Support" links** open upstream's repository and chat room. BSD-2-Clause does not ask a copy to offer its own source, so they stay as upstream has them.
- Upstream's other switches keep upstream's defaults: Home Assistant support and reverse-proxy sign-in are off, and `DEBUG` is off.

## Start-up when several starts run at once

- **What happened before this pin.** When a new deployment gets its first requests, Tofu's container hosting starts the app several times within a second or two; the instances share the database and nothing else. Each start ran `migrate`. On a new, empty database they made the same tables at the same moment and crashed against each other: the live checks of 2026-10-26 logged 12 and 20 such errors (`already exists`, `duplicate key`) in two first deployments, `relation "django_admin_log" already exists` among them, and a crashed start answers 500. Every statement also goes through Tofu's transaction pooler, a round trip each, and `migrate` sends 1,447 statements on an empty database and 717 with nothing to apply (its post-migrate steps run once for every app): later starts did not listen on their port within the 28 seconds the hosting waits ("your server did not accept TCP connections on that port within the startup timeout", 3 and 19 times), and both first deployments stayed "building" for more than ten minutes. All 37 tables the app had made were open to the database's Data API.
- **The schema step.** `tofu-entrypoint.sh` runs `python manage.py tofu_schema` (`babybuddy/tofu_schema.py`) before gunicorn. Under the lock below, a start reads what the database holds and does only what is left:
  - none of the app's tables: it applies the snapshot `babybuddy/tofu_schema.sql` in one statement inside one transaction, then runs `migrate` for any migration newer than the snapshot;
  - migrations left to apply (a database that is behind, or a snapshot that does not match the code): it runs `migrate`, each migration in its own transaction as upstream's `migrate` does;
  - up to date: it does not run `migrate`.

  Then it turns on row-level security on every table of the app that lacks it, and lets the lock go. The runtime log gets one line, for example `tofu_schema: empty database: applied the snapshot of 107 migrations in 0.15s (0.01s waiting for the lock)` or `tofu_schema: up to date in 0.28s (0.24s waiting for the lock)`.
- **The lock.** `locked_schema_step` opens a second connection with the app's own database settings, so through the same transaction pooler, and starts a transaction whose first statements are `SET LOCAL lock_timeout = '120s'`, `SET LOCAL idle_in_transaction_session_timeout = 0` and `SELECT pg_advisory_xact_lock(1015805802)` (a fixed key, `zlib.crc32(b"babybuddy:tofu-schema")`, the same in every start). That transaction writes nothing and stays open while the start does the schema work on Django's own connection; it is rolled back afterwards, and the lock ends with it. It is a transaction-level lock because a transaction pooler hands the server connection to other clients between transactions: a session-level lock (`pg_advisory_lock`) taken through it would stay with a server connection that others then use, or be lost with it. An open transaction keeps its one server connection until it ends, so the lock holds for exactly as long as the transaction, and goes when the transaction ends, by the rollback or because the start died and its connection dropped. The settings are `SET LOCAL`, so nothing stays on the pooler's server connection either.
- **Waiting.** A start that finds the lock taken waits for it at most 120 seconds (`lock_timeout`), then fails, and `tofu-entrypoint.sh` tries again five seconds later, five times at most. A start that gets the lock always reads the database's state again under it, so it never assumes the database is still empty. A start that still meets a duplicate-object error (a duplicate table, object or column, or a unique violation) runs the whole step once more.
- **The snapshot.** `babybuddy/tofu_schema.sql` (570 KB) is what `migrate` leaves on a new database with Tofu's settings, taken by pg_dump from a scratch database that `migrate` brought up to date: the 37 tables with their indexes, constraints and sequences, and their rows (the content types and permissions, the read-only and caregiver groups and their permissions, the default nap times, the 7,428 rows of growth percentiles from `core/0030` and `core/0033`), without pg_dump's session settings and psql commands; then `django_migrations` with the 107 migrations, recorded as applied when the snapshot is loaded, and row-level security on every table. A database loaded from it and one made by `migrate` give the same pg_dump, apart from row-level security. Its first line lists the 107 migrations with the SHA-256 of each file. A start uses the snapshot only on a database that has none of the app's tables, and only when every migration it lists is in the code with the same file; otherwise it runs `migrate` from the beginning. Migrations added later (newer upstream code) run through `migrate` after the snapshot. To make the snapshot again after the migrations change, run `DJANGO_SETTINGS_MODULE=babybuddy.settings.tofu DATABASE_URL=<an empty scratch PostgreSQL database> python manage.py tofu_schema --make-snapshot` with `pg_dump` on `PATH`; `babybuddy/tests/tests_tofu_schema.py` fails while the snapshot does not match the code's migrations.
- **Statements a start sends**, counted on a scratch PostgreSQL 14 with `log_statement = 'all'`: a first start on an empty database 10 (it was 1,447), a start on a database that is up to date 9 (it was 717). Two of each are Django setting the connection's time zone, which it sends only when the server's own is not UTC. Through the pooler that is ten round trips, plus the snapshot's own time on the server (0.15 seconds here).
- **Row-level security.** In the same locked step, `ALTER TABLE … ENABLE ROW LEVEL SECURITY` for each table of the app that lacks it: the tables of its models (Baby Buddy's own, Django's, django-axes', Django REST framework's tokens, dbsettings' and the webhooks'), `django_migrations` and the cache table `cache_default`, 37 in all, when they are in `public` and owned by the app's role. There is no policy, so the Data API's roles (`anon`, `authenticated`) read no row and write none, while the app's own connection owns the tables and is not limited by it. Tables the app's code does not make are left as they are. It costs one query when nothing is left to close. A copy made from an earlier pin gets its tables closed at its next start, and a table a later migration adds is closed by the start that adds it.
- **The five-starts test** (on this machine, no Docker; see "Verification"): five copies of the image's start command, each on its own port, started at the same instant against one empty database whose new tables are open to `anon`, `authenticated` and `service_role` as on Tofu's databases made before 2026-10-30. On `pin/2026-10-25.1` (three runs) four of the five starts crashed in `migrate` and retried after five seconds; the logs held 12 lines with `already exists`, 10 to 12 with `duplicate` and 16 tracebacks, and none of the 37 tables had row-level security (`anon` read a row from each of the 9 that held any). On this pin, three runs: one start applied the snapshot and four waited for it and found the database up to date, all five answered `/` (through its two redirects, `/first-account/` with 200) within 1.3 seconds of being started, none exited, the logs held none of those lines, and all 37 tables had row-level security.

## Needs a real deploy to verify

- The image builds on Tofu's container hosting: `python:3.13-slim` from Docker Hub, and 47 packages from PyPI, all as wheels.
- The schema step through Tofu's transaction pooler: the lock's transaction (`SET LOCAL`, then `pg_advisory_xact_lock`, kept open while the step runs) and the snapshot (570 KB of SQL in one statement) pass through it as they do through a direct connection, and a first start listens on its port well within the 28 seconds the hosting waits. `/` then answers through two redirects (`/login/`, then `/first-account/`, which answers 200).
- That a start which dies while it holds the lock lets the lock go through the pooler too. Here, on a direct connection, a holder killed in the middle of its transaction let it go at once.
- Which scheme and host Tofu's proxy passes on. Forms (signing in included) work when either the scheme and host Django reads from the proxy's headers, or `CSRF_TRUSTED_ORIGINS`, match the address in the visitor's browser; when neither does, every form answers Baby Buddy's "CSRF verification failed" page, which names the address it refused. A domain the owner connects later works through the proxy's headers; if it does not, add its `https://` address to `CSRF_TRUSTED_ORIGINS`, separated by a comma.
- Kept connections through the pooler: the runtime logs show no `server closed the connection unexpectedly` and no cursor errors (Django's errors reach the runtime log, see "What Tofu changes").
- Importing data in the admin (django-import-export's **Import**, then **Confirm import**). Between the two steps the uploaded file waits in the container's temporary folder, upstream's default. If Tofu sends the second step to another instance of the app (it does run several at once, see "Start-up when several starts run at once"), or restarts it in between, the confirmation fails and the import has to be started again; nothing is imported by halves.
- Whether sign-in lockout sees each visitor's own address. Baby Buddy (django-axes) locks an address out for an hour after five failed sign-ins, and reads the address from `X-Forwarded-For`. If Tofu's proxy passed one address for everyone, five failures from anyone would lock everyone out; if it passed a visitor's own `X-Forwarded-For` unchecked, a visitor could dodge the lockout.
